# 分流机制

这是本项目的核心。理解了这一页,就理解了整个程序在做什么。

## 两类入站

生成的 sing-box 配置里有这些入站:

| 入站 tag | 监听 | 行为 |
| --- | --- | --- |
| `in-main` | `7890`(可改) | 走 `proxy` 选择器(所选节点 / `auto` 自动测速 / `direct`) |
| `in-tun` | 网卡 `sbr-tun` | 同上,但透明捕获全部程序(见 [tun.md](tun.md)) |
| `in-<节点id>` | 每节点一个,默认 `20800` 起 | **直绑该节点出站**,流量固定从这个节点出去 |
| `in-<直连节点id>` | 虚拟【直连】节点 | **直绑内置 `direct`**,任何模式下都不经代理 |

节点端口在面板里可以逐个手改,也可以「重排端口」从起始值连续重新分配。改动点「应用配置」生效 —— 内核在跑的话会先停再起(几秒钟),系统代理接管与还原自动跟着走。

## 规则顺序是一条不变量

sing-box 路由是**首个匹配生效**。所以规则的先后不是风格问题,而是正确性问题:

```jsonc
"route": {
  "rules": [
    { "inbound": ["in-main", "in-tun"], "action": "sniff" },
    { "protocol": "dns", "action": "hijack-dns" },
    { "port": 53, "action": "hijack-dns" },          // 仅 TUN 开启时

    // ★ 节点直绑:谁连这个端口,就从这个节点出去
    { "inbound": ["in-n_a1b2c3"], "outbound": "香港 01" },
    { "inbound": ["in-n_d4e5f6"], "outbound": "日本 02" },
    // ★ 虚拟直连节点:绑内置 direct
    { "inbound": ["in-d_704acb"], "outbound": "direct" },

    // ↓ 以下只对主端口 / TUN 生效
    { "clash_mode": "direct", "outbound": "direct" },
    { "clash_mode": "global", "outbound": "proxy"  },

    // ★ 你在面板里写的自定义规则,按列表顺序展开
    { "process_path_regex": ["^/usr/lib/firefox/.*$"], "outbound": "proxy" },
    { "ip_cidr": ["198.51.100.0/24"], "outbound": "direct" },
    { "domain_regex": ["^.*\\.ads\\.example$"], "action": "reject" },

    { "domain_suffix": [".local", ".lan", "…"], "outbound": "direct" },
    { "ip_is_private": true, "outbound": "direct" },

    // 仅「国内自动分流」开启时:最宽泛的一层猜测,所以排最后
    { "rule_set": ["geosite-cn"], "outbound": "direct" },
    { "rule_set": ["geoip-cn"],   "outbound": "direct" }
  ],
  "final": "proxy"
}
```

七层,自上而下越来越宽泛:

| | 层 | 谁决定的 |
| --- | --- | --- |
| 1 | `sniff` / `hijack-dns` | 协议层,必须最前 |
| 2 | 节点端口直绑 | 你在端口上写死的意图 |
| 3 | `clash_mode` 模式开关 | 你在下拉框里选的 |
| 4 | 自定义分流规则 | 你写的规则 |
| 5 | 私有地址与内网域名 | 内置安全兜底 |
| 6 | 国内自动分流(可选) | 规则集里的数据在猜 |
| 7 | `final: proxy` | 兜底 |

有三条顺序约定:

**1. 直绑规则必须排在 `clash_mode` 之前。**

否则一旦你在面板里把模式切成「全局代理」或「全局直连」,`clash_mode` 规则会先匹配上,所有端口绑定被**静默推翻** —— 端口还在监听,流量却全跑到了别的出口,而界面上看不出任何异常。

这条曾经真的踩过:模式被误切到 global 后,所有独立端口一起失效。语义上也应该如此 —— 独立端口是用户**显式**指定的「这个端口固定走这个节点」,而模式开关的职责只是影响**全局**流量。

**2. 直绑规则必须排在私有地址等通用规则之前**,否则发往内网的流量会被通用规则截走,而不是按你指定的节点走。

**3. 自定义规则必须排在私有地址兜底与国内自动分流之前。**显式压隐式:你专门写下的一条规则,不该被「内置觉得这是内网」或「规则集觉得这是国内」推翻。

自检里有专门的断言守着这几条:

```
✓ ★ 直绑规则必须排在 clash_mode 之前（全局模式不能覆盖端口绑定）
✓ ★ 直连节点在 direct 与 global 两种模式下都保持直连
✓ ★ 开 TUN 后，每节点端口与直连节点依然优先于 clash_mode
✓ ★ 自定义规则排在 clash_mode 之后、私有地址兜底之前
✓ ★ 端口直绑依然优先于自定义规则
✓ ★ 国内分流排在所有显式规则之后（它是最宽泛的一层猜测）
```

## 虚拟【直连】节点

点节点页的「+ 直连节点」加一个。它是个伪节点:

- **没有远端服务器**,不产生任何 `outbound` 对象
- 只占一个本地端口,该端口的路由规则直接绑内置 `direct`
- **不出现**在 `outbounds`、`proxy` 选择器和 `auto` 测速组里
- 没有延迟测试(测它没意义,面板里也不显示测速按钮)

用途是给个别程序开后门,比域名规则精确得多:

```bash
# 假设它分到 20807
curl -x http://127.0.0.1:20807 https://myip.ipip.net    # 显示你的真实 ISP 出口
git config --global http.proxy http://127.0.0.1:20807   # git 直连,其余照常走代理
```

因为它的绑定规则也排在 `clash_mode` 之前,所以**即使你把模式切成「全局代理」,走这个端口的流量依然直连**。这是刻意的:你显式建了一个叫「直连」的端口,它就该永远直连。

## 自定义分流规则

面板「分流规则」页。一条规则 = **域名 / IP / 进程三栏的任意组合 → 同一个去向**(直连 / 走代理 / 拦截 / 某个具体节点),命中其中任意一项就进这个去向:

| 栏 | 写法 | 生成的字段 | 正则 |
| --- | --- | --- | --- |
| 域名 | `github.com` | `domain_suffix`(含所有子域名) | |
| | `re:^.*\.cn$` | `domain_regex` | ✅ `re:` 前缀 |
| 进程 | `telegram-desktop` | `process_name` | |
| | `/usr/bin/curl` | `process_path`(`/` 开头 = 完整路径) | |
| | `re:^/usr/lib/firefox/` 或裸写 `^/usr/lib/firefox/` | `process_path_regex` | ✅ 自动识别 |
| IP | `198.51.100.0/24` · `198.51.100.7` | `ip_cidr`(裸 IP 自动补 `/32` / `/128`) | ❌ |

一栏里可以填多个值,**换行或逗号**分隔,内部去重后保持你写的顺序。

**输入会被规范化,不用自己清:** 域名栏会剥掉协议前缀、路径与查询串、前导 `*.`(Clash 写法)、首尾的点,并统一小写 —— 直接从地址栏整段粘贴 `HTTPS://GitHub.com/path?q=1` 会存成 `github.com`。非法值(`256.1.1.1`、`/33`)在保存时就报错。

### 正则的两个硬约束

**IP 没有正则。** sing-box 的 IP 匹配走前缀树(radix trie),拿的是 32/128 位整数而不是字符串,内核里压根没有可以跑正则的地方。所以填了正则会被明确拒绝,并提示改用 CIDR、或者改成域名正则 —— 而不是默默存下来,等内核启动时报一句看不懂的错。

**正则是 Go 的 RE2,不是 JS 的。** 下面这些 JS 能编译、内核不能:

| 写法 | 说明 |
| --- | --- |
| `(?=…)` `(?!…)` | 前向断言 |
| `(?<=…)` `(?<!…)` | 后向断言 |
| `\1` | 反向引用 |
| `(?<name>…)` | 命名分组,Go 的写法是 `(?P<name>…)` |

这些在**保存时**就被拦下。不拦的话结果是「保存成功」+ 内核起不来,排查起来极其难受。反过来,合法的 Go 写法 `(?P<name>…)` 必须放行 —— 校验时会先把它翻译成 JS 语法再送去编译,只借 JS 引擎做语法体检,不让 JS 的方言差异误伤用户。

### 顺序即优先级

规则列表用 ↑↓ 调整顺序,顺序**直接**决定生成配置里的先后 —— 首个匹配生效,所以这不是外观功能。写两条冲突的规则时,上面那条赢。

### 指向具体节点的规则

去向选一个节点时,生成的是该节点的出站 tag(选虚拟【直连】节点则是 `direct`)。如果这个节点后来被停用或删除:

- 这条规则**不会**进配置 —— 绝不生成指向不存在 tag 的规则,那会让内核直接拒绝启动
- 但启动前的自检会明确报出来:`分流规则「…」指向的节点已禁用,该规则不会生效`

静默丢弃是最糟的失败方式,所以宁可在启动前多说一句。

### 例子

```
进程   re:^/usr/lib/firefox/                       → 走代理
进程   telegram-desktop                            → 走代理
域名   github.com, githubusercontent.com           → 走代理
域名   re:^.*\.(cn|com\.cn)$                       → 直连
域名   ads.example                                 → 拦截
IP     192.168.50.0/24                             → 直连
IP     198.51.100.7                                → 香港 01
```

## 国内自动分流

面板「设置 → 国内自动分流」。开启后,命中 `geosite-cn` 的域名和命中 `geoip-cn` 的 IP 走直连,其余走代理。**默认关。**

### 先下到本地,再引用

早先的版本让内核自己远程拉规则集,结果**从来没成功过**:启动 0.03 秒、日志里没有任何 rule-set 行、`cache.db` 一直是空的 —— 开关等于没接线,而界面上完全看不出来。

现在默认是**本地文件优先**:

```bash
node scripts/cli.mjs get-geoip                        # 下到数据目录的 rulesets/
node scripts/cli.mjs get-geoip --mirror https://ghfast.top/   # 被墙就走镜像
```

面板设置里的「下载 / 更新规则集」按钮做的是同一件事,并且会显示每份文件的**大小和下载时间** —— 能看见文件,才谈得上「开关生效了」。下载会校验 `.srs` 的魔数,挡住下到 HTML 错误页却当成规则集存下来的情况。

| `rulesetSource` | 行为 |
| --- | --- |
| `auto`(默认) | 两份都在就用本地;缺就让内核远程拉 —— 不必先手动下一遍才能开开关 |
| `local` | 只用本地。缺文件时**启动前**就报错并说明怎么补,绝不产生启动期下载 |
| `remote` | 始终远程,内核按 `rulesetUpdateInterval`(默认 `7d`)自己更新 |

远程模式生成的引用带 `download_detour: "proxy"` —— 规则集本身在墙外,直连大概率拿不到,这正是上个版本静默失败的根因。

### 为什么没有全局 `action: "resolve"`

域名侧由 `geosite-cn` 负责,命中即直连,不需要先解析成 IP。`geoip-cn` 那条匹配的是「目标本来就是 IP」的连接(大量 App 直连 IP)以及嗅探已知 IP 的情况。

刻意不插一条全局 `resolve`:那会给**每条**代理连接都加一次本地解析,既慢,又容易把本该整域名交给代理的连接降级成 IP 连接(丢掉 SNI、破坏基于域名的路由)。

### DNS 要配套

开启后 DNS 侧会多一条 `{ "rule_set": ["geosite-cn"], "server": "dns-local" }`:国内域名用国内 DNS 解析。这不只是为了快 —— 拿到就近 CDN 的**中国 IP**,`geoip-cn` 那条规则才真的命中得上。用国外 DNS 解析国内域名,很可能拿到境外 IP,于是国内网站反而走了代理。

### 关掉之后

配置里零 `.srs` 引用,没有任何启动期下载依赖,离线也能起。自检里有断言守这条。

## 主端口与选择器

主端口(和 TUN)走的是 `proxy` 选择器,它由三部分组成:

```jsonc
{
  "type": "selector",
  "tag": "proxy",
  "outbounds": ["auto", "香港 01", "日本 02", "…", "direct"],
  "default": "auto"
}
```

- `auto` 是 `urltest` 出站,按 `testUrl` 每 3 分钟测一轮,容差 150ms
- `direct` 也放进了选择器,所以主端口可以整体切直连,不用改配置
- 面板顶栏的下拉框改的就是这个选择器,通过 Clash API 热切换,不重启内核

没有任何真实节点时,`proxy` 退化为只含 `direct`,内核照样能起来 —— 空节点列表不应该让程序启动失败。

## DNS

| | 协议 | 走向 |
| --- | --- | --- |
| 国内域名 / 内网域名 | UDP `223.5.5.5` | 直连,快 |
| 其余 | **DoT(TLS/853)** `8.8.8.8` | 经 `proxy` 出站 |

开启「国内自动分流」后,`geosite-cn` 命中的域名也走 `dns-local`(见上文)。

国外 DNS 刻意不用 UDP:UDP DNS 穿代理依赖出站的 UDP 转发能力,很多节点上会超时或丢包,表现就是「网页能连但域名解析不了」这类怪错误。DoT 基于 TCP,任何代理都能稳定承载。

`route.default_domain_resolver` 指向 `dns-local`,让 `direct` 出站解析域名时用国内 DNS。
